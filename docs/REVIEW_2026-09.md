# 코드 리뷰 후속 개선 (2026-09)

v2 완성 후 프론트엔드·백엔드·DB·설정 전체를 다시 검토한 기록입니다. 우선순위는 **아키텍처 = 보안 = 성능 > 가독성**.
진행 순서: 파악(빌드·테스트·린트·의존성 감사) → 진단 → 승인된 항목만 수정 → 셀프 리뷰.
모든 결함은 "재현 → 근본 원인 → 수정 → 재발 방지 테스트 → 재검증" 순서로 처리했고, 성능 수치는 측정값만 적었습니다.

## 3. 변경 기록

### SEC-01 요청 제한의 클라이언트 IP 위조 차단
- **원인**: `server.forward-headers-strategy: framework` 의 `ForwardedHeaderFilter` 는 `X-Forwarded-For` 의 맨 앞 값(클라이언트가 임의로 넣을 수 있음)을 `getRemoteAddr()` 로 씁니다. 로컬 재현: 같은 IP 로 11번째 시도는 429 였지만, 헤더만 바꾸면 12번 모두 401.
- **수정**: `native`(Tomcat RemoteIpValve) 로 바꿔 헤더를 **오른쪽(프록시가 덧붙인 값)부터** 읽고 신뢰할 프록시를 건너뛴 첫 주소를 씁니다. `ClientIp` 가 프록시가 붙이는 포트를 떼어 냅니다. 여러 IP 에서 오는 대입 공격에 대비해 계정당(10분 20회, 성공 시 초기화)·공유 링크당(10분 50회) 제한을 추가했습니다(동작 변경).
- **검증**: `ClientIpRateLimitTest`(실제 Tomcat, 수정 전 실패 → 수정 후 통과), `ClientIpTest`, `AuthFlowTest`·`ShareLinkTest` 추가 케이스.

### SEC-02 권한이 사라진 뒤의 WebSocket 수신 차단
- **원인**: 구독 권한은 SUBSCRIBE 순간에만 검사됩니다. 로컬 재현: 제외된 사용자에게 REST 는 404 였지만 WebSocket 으로는 제외 뒤의 메시지가 도착.
- **수정**: `TeamSubscriptionTracker`(이전 `PresenceTracker`)가 팀 토픽 구독을 (세션, 구독) 단위로 추적하고, 제외·나가기·탈퇴가 커밋되면 `SimpleBrokerMessageHandler` 의 구독 레지스트리에서 해당 구독을 해제합니다(연결은 유지). `WebSocketSessionExpiry` 가 로그인이 만료된 세션을 1분 안에 닫고, 인터셉터는 만료 후의 프레임을 거절합니다. 프론트는 제외 알림을 받으면 그 팀 화면에서 나가고, 재연결 시 팀 목록을 다시 받습니다. 이 과정에서 `/teams/1` 이 `/teams/12` 에도 일치하던 경로 비교도 고쳤습니다.
- **검증**: `WebSocketSecurityTest` 2건(수정 전 실패 → 통과), `WebSocketSessionExpiryTest`, 프론트 `useOnReconnect`·`isTeamPath` 테스트.

### SEC-03 Tomcat 패치 버전 고정
- Spring Boot 4.1.x 최신이 4.1.1(Tomcat 11.0.24)이라 `build.gradle.kts` 의 의존성 제약으로 11.0.26 을 지정. OSV 재조회 결과 런타임 의존성 138개 중 알려진 취약점 0건. Boot 를 올릴 때 제약을 지우도록 주석을 남겼습니다.

### SEC-08 / SEC-09
- 무결성 위반 로그는 Hibernate 가 추출한 제약 이름만 기록합니다(`GlobalExceptionHandlerTest`, 로그 캡처로 검증).
- `application-prod.yml` 의 CORS 허용 출처 기본값을 비웠습니다(`CorsProfileTest`, 실제 설정 파일을 우선순위대로 바인딩해 검증).

### BUG-01 72바이트를 넘는 비밀번호
- **원인**: `@Size(max = 72)` 는 글자 수, BCrypt 는 UTF-8 72바이트까지만 처리하고 넘으면 `IllegalArgumentException`.
- **수정**: `@MaxUtf8Bytes(72)` 제약을 가입·공유 링크 비밀번호에 적용 → 400 + 필드 메시지.

### BUG-02 화면 경로 새로고침 404
- **원인**: 화면 경로를 `SpaController` 에 나열해, 목록에서 빠진 `/search` 는 404.
- **수정**: "첫 경로 조각이 서버 경로(api·ws·actuator·v3·swagger-ui·assets·error)가 아니고 점(.)이 없는 GET" 규칙으로 판단. `SpaRoutingTest`(14건)와 E2E(새로고침) 추가.

### BUG-03 / ARC-01 업로드 취소와 오류 처리
- **원인**: abort 이벤트는 한 번만 발생하는데, 대기 중에 이미 취소된 신호에 리스너를 나중에 달아 요청이 그대로 전송됨(테스트에서 5초 타임아웃으로 재현).
- **수정**: 취소된 신호는 보내지 않고 대기열에서 제거, '취소됨' 표시. XHR 업로드도 공통 `toApiError`·`notifyUnauthorized` 와 CSRF 재시도를 거칩니다.

### BUG-04 편집기 앱 내 이동
- **원인**: `beforeunload` 는 창 닫기·새로고침에만 발생.
- **수정**: `useBlocker` 로 앱 내 이동을 막고 확인. `useBlocker` 가 데이터 라우터 전용이라 진입점을 `createBrowserRouter` + `RouterProvider` 로 감쌌습니다(화면 경로 정의는 그대로). 대가로 라우터 엔진이 들어가 첫 화면 JS 가 133KB → 151KB(gzip +18KB, 측정) 늘었습니다 — 편집 내용 유실 방지가 더 중요하다고 판단했습니다.

### BUG-05 / BUG-06
- 휴지통 자동 비우기 시각·시간대를 설정값으로(기본 Asia/Seoul 04:00). 테스트 JVM 을 UTC 로 고정해 개발 PC(KST)에서만 통과하는 테스트가 생기지 않게 했습니다(`TrashPurgeScheduleTest`, TZ=UTC 에서 실패 → 통과).
- 클립보드를 쓸 수 없으면 편집본을 파일로 내려받고 사실대로 안내합니다.

### PERF-01 저장소 입출력을 트랜잭션 밖으로

|---|---:|---:|
| 업로드가 저장소에 쓰는 동안 점유 커넥션 | 1 | 0 |
| 복사가 저장소에서 복사하는 동안 점유 커넥션 | 1 | 0 |

### BUG-07 CSRF 발급 API 의 토큰
- **발견**: SEC-06 을 운영 이미지에서 검증하는 스크립트가 `GET /api/auth/csrf` 응답의 `token` 을 헤더로 보냈는데 403(CSRF_INVALID). 응답 값이 쿠키 값과 달랐습니다.
- **원인**: 컨트롤러 인자 `CsrfToken` 은 BREACH 방어용으로 매번 가린(masked) 값인데, SPA 방식 CSRF 는 헤더를 쿠키의 원래 값으로 비교합니다. 프론트는 쿠키를 읽어 영향이 없었지만, API 문서대로 쓰는 클라이언트는 실패합니다.
- **수정**: `CsrfFilter` 가 요청에 넣어 두는 `DeferredCsrfToken` 에서 원래 값을 돌려줍니다. 이 응답에는 사용자 입력이 섞이지 않아 BREACH 전제가 성립하지 않습니다.
- **검증**: `CsrfEndpointTest` — 실제 서버에서 응답 토큰이 쿠키와 같고 헤더로 쓰면 204 (수정 전 실패). MockMvc 의 `csrf()` 도우미가 공유 필터의 저장소를 바꿔 이 계약은 실제 HTTP 로 검증합니다.

### BUG-08 CSRF 토큰이 요청마다 바뀌던 문제
- **발견**: BUG-07 을 고친 뒤에도 브라우저 검증 스크립트가 403. 쿠키 목록을 보니 `/api/auth/csrf` 가 돌려준 토큰과 잠시 뒤의 쿠키 값이 달랐고, curl 로 확인하니 **로그인한 상태의 모든 요청**(예: `GET /api/teams`)이 `XSRF-TOKEN` 을 지우고 새로 발급했습니다.
- **원인**: 세션 없이 요청마다 쿠키로 인증하므로, Spring Security 의 세션 관리 필터가 매 요청을 "새로 인증됨"으로 보고 CSRF 인증 전략(`CsrfAuthenticationStrategy`)을 실행해 토큰을 교체했습니다. 요청이 겹치면 헤더로 보낸 토큰과 브라우저가 붙인 쿠키가 어긋나 403 이 났고, 프론트의 "CSRF 오류 시 1회 재시도"가 이를 가려 테스트·E2E 가 통과했습니다.
- **수정**: CSRF 설정의 세션 인증 전략을 끄고(`NullAuthenticatedSessionStrategy`), 교체는 로그인·가입·로그아웃 응답에서 CSRF 쿠키를 지워 다음 변경 요청 전에 새 토큰을 받게 하는 방식으로 그 시점에만 합니다.
- **검증**: `CsrfEndpointTest` — 로그인한 요청은 CSRF 쿠키를 보내지 않음, 가입 응답은 CSRF 쿠키를 지움 (둘 다 수정 전 실패).

### SEC-05 저장 공간 한도와 가입 제한 (기능 추가)
- **문제**: 누구나 가입해 파일을 올릴 수 있는데 저장량 한도가 없어, 계정을 여러 개 만들어 올리면 저장 비용이 제한 없이 늘 수 있었습니다.
- **수정**: `StorageQuota` — 개인 1GB·팀 5GB(설정값). 사용자가 보는 파일 크기가 아니라 **실제 저장량(옛 버전·휴지통 포함)** 으로 셉니다(텍스트를 반복 저장해 버전을 한없이 쌓지 못하게). 업로드·텍스트 저장·복사 모두 확인하고, 사용량 API 에 `storedBytes`·`quotaBytes` 를 추가해 화면에 막대로 보여 줍니다. 가입은 IP 당 시간당 5회.
- **동시성**: 저장 직전 저장소 주인(사용자·팀) 행을 잠가 줄 세웁니다. 처음 구현은 잠금을 기다린 뒤에도 합계를 일반 읽기로 세서, MySQL 기본 격리 수준(REPEATABLE READ)의 스냅샷 때문에 먼저 커밋된 업로드를 보지 못해 **10KB × 8개 동시 업로드가 64KB 한도에서 8개 모두 성공**했습니다(테스트로 발견). 합계를 잠금 읽기(`FOR SHARE`)로 바꿔 최신 커밋 데이터를 세도록 고친 뒤 정확히 6개만 성공합니다(반복 실행 확인).
- **함께 찾은 결함**: 요청 제한기의 오래된 키 정리가 "10분"으로 고정돼, 1시간짜리 창(가입 제한)의 기록이 30분 만에 지워질 수 있었습니다 → 지금까지 쓰인 가장 긴 창 기준으로 정리.
- **검증**: `StorageQuotaTest` 7건(한도 초과 시 저장소에 파일을 남기지 않음, 휴지통·버전 포함, 복사, 팀 한도, 동시성), `SlidingWindowRateLimiterTest`, `AuthFlowTest`(가입 제한), 프론트 `StorageMeter.test`.

### SEC-06 체험 계정 보호 (기능 추가)
- **문제**: 데모 모드는 체험 비밀번호를 로그인 화면에 공개하므로, 한 방문자가 체험 계정을 탈퇴시키거나 체험 팀을 지우면 다른 방문자의 체험이 망가졌습니다.
- **수정**: `DemoAccounts` — 체험 계정은 탈퇴·팀 삭제·팀장 위임·팀 나가기, 체험 계정을 팀에서 내보내기를 할 수 없습니다(403, "체험 데이터는 주기적으로 초기화됩니다"). 체험 계정의 개인 저장소와 체험 계정이 팀장인 팀에는 체험 한도(50MB)를 적용합니다. `DemoDataSeeder.reset` 이 매일 05:00(Asia/Seoul) 체험 계정이 팀장인 팀과 체험 계정을 지우고 처음 상태로 다시 만듭니다. 이를 위해 팀·계정 삭제를 "권한 확인"과 "실제 삭제(`purgeTeam`·`purgeAccount`)"로 나눴습니다. 일반 사용자 데이터는 건드리지 않습니다.
- **검증**: `DemoProtectionTest` 3건(차단되는 작업, 체험 한도, 초기화 후 복원·일반 사용자 데이터 보존). 데모 모드를 켠 테스트 컨텍스트가 생기면서 백엔드 라인 커버리지 83.7% → 89.0%.

## 5. 병합 후 후속 — 불안정한 E2E

- **현상**: 개선 PR 5개를 병합한 뒤 `main` CI 에서 E2E 한 시나리오(팀 문서 편집·저장 후 버전 기록 확인)가 실패했습니다. 같은 코드가 PR 단계와 로컬에서는 통과했습니다.
- **원인**: 코드가 아니라 테스트의 선택자였습니다. 버전 기록 대화상자에서 `getByText('현재 버전')` 은 부분 일치라 하단의 `현재 버전에 서명` 버튼과도 일치해, 버전 목록이 늦게 오면 버튼 하나만 잡혀 **엉뚱한 요소로 통과**하고, 빨리 오면 뱃지와 버튼이 함께 잡혀 strict mode 위반으로 실패했습니다.
- **수정**: `{ exact: true }` 로 뱃지만 검증합니다(검증을 느슨하게 한 것이 아니라 의도한 요소를 정확히 봄). E2E 는 모든 요청이 한 IP·같은 체험 계정으로 로그인해 운영 한도(분당 10회)에 가까우므로, docker-compose 가 `LOGIN_RATE_PER_MINUTE`·`LOGIN_ACCOUNT_RATE` 를 받게 하고 CI 의 E2E 작업만 200 으로 올렸습니다(운영 기본값은 그대로).
