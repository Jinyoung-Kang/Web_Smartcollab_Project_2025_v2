## 1. 발견 사항 (심각도순)

### 치명 — 이미 운영에 임시 조치함

**C-1 · 신뢰성 · 확인: 재현**

| 항목 | 내용 |
|---|---|
| 문제 | JDK 21 가상 스레드가 Azure SDK 의 `BlobInputStream.read` 에서 캐리어 스레드에 묶입니다. 이 메서드는 `synchronized` 안에서 동기 다운로드를 기다리기 때문입니다. 그런데 SDK 의 응답 처리도 가상 스레드에서 돌아서, 처리할 캐리어가 없습니다. 내려받기·미리보기·편집기 열기·공유 내려받기·AI 문서 읽기가 모두 이 경로를 탑니다. |
| 영향 | 캐리어가 1개(B1 = 1 vCPU)면 큰 파일을 **한 번만** 내려받아도 서버 전체가 영구히 멈춥니다. 헬스 체크도 응답하지 않습니다. |
| 재현 | 로컬 `-XX:ActiveProcessorCount=1` + 실제 Azure Blob 에서 30MB 를 1건 내려받음 → 10분 넘게 헬스 체크 무응답. 덤프에서 `parkOnCarrierThread` 확인. 작은 파일(1MB 미만)은 정상. |
| 임시 조치 | 운영 앱 설정 `SPRING_THREADS_VIRTUAL_ENABLED=false` (07:27Z). 같은 로컬 조건에서 30MB 1건 1.4초, 8건 동시면 16건이 9.5초. 운영에서는 30MB 1건·2건 동시가 6.7~8.4초에 정상이고, 그동안 헬스 체크 중앙값 175ms. |

운영 JVM 이 실제로 CPU 를 몇 개로 보는지는 확인하지 못했습니다(앱 컨테이너 SSH 가 막혀 있음). B1 은 1 vCPU 라서 노출됐을 가능성이 높습니다.

## 3. 하지 않는 것과 이유

- **같은 내용 저장을 서버에서 막기**: 명시적인 저장이 버전을 남기는 것이 의도인지 코드만으로 알 수 없습니다. 화면의 버그(M-5)만 고칩니다.
- **Java 24+ 로 올리기**(가상 스레드 고정 해소): App Service 의 Java 런타임은 21 까지이고, 컨테이너 배포로 바꾸면 인프라가 바뀝니다.
- **Blob 내려받기를 직접 만든 범위 스트림으로 바꾸기**: 가상 스레드를 끄면 필요 없습니다. 가상 스레드를 다시 켤 때 함께 검토합니다(ADR-0014 에 적음).
- **B1 기동 시간(129~236초) 줄이기**: 새 컨테이너가 준비될 때까지 이전 컨테이너가 계속 응답하므로 사용자에게 보이는 중단이 없습니다. 대기 한도도 600초로 올렸습니다. CDS 등은 시작 명령을 바꿔야 해서 효과에 비해 위험합니다.
- **기존 결정 유지**: 남은 양방향 모듈 의존 4쌍과 `drive` 통합, `AccessPolicy` 인자 바꾸기, 접근 코드 잠금 상수의 설정화, AI 상한의 설정화는 하지 않습니다. 비용·위험에 비해 이득이 작고, 모델을 바꿀 계획도 없습니다.
- **측정 없이 고치지 않음**: 휴지통·버전 목록 페이지 나누기, 가상 스크롤은 측정에서 문제가 보일 때만 합니다.
- **IPv6 로 IP 단위 제한 우회**: 배포에서 IPv6 인바운드가 켜져 있는지 확인되지 않았습니다.
