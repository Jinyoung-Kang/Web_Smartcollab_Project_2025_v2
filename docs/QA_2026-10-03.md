# 출시 기준 QA — 계획과 결과 (2026-10-03, `main` `5a89d95` 기준)

> **상태: 완료(병합 대기) — 2026-10-03 소유자 승인(D1~D6 권장안).** 결과는 [9. 결과](#9-결과), 원자료는 [qa/results](../qa/results) 에 있습니다.

## 0. 목적과 원칙

- **목적.** 실무 출시 기준으로 결함을 찾습니다. 결함마다 재현하고 실패하는 시험으로 증명한 뒤, 근본 원인을 고쳐 같은 시험이 통과하게 합니다.
- **범위.** 기능 정확성, 신뢰성, 성능 효율성, 보안, UI/UX·접근성을 봅니다.
  - 보안 결함과 데이터 손실 위험을 가장 먼저 봅니다.
  - 계층 위반·순환 의존 같은 아키텍처 문제는 결함과 나눠 **개선 제안**으로 적습니다.
- **증거 없는 결함은 적지 않습니다.**
  - 재현하지 못한 의심은 **미확인** 으로 따로 둡니다.
  - 문서(ADR·SECURITY 의 "알려진 한계")에 적힌 의도된 동작은 결함이 아닙니다. 예: 로그아웃 뒤에도 이미 탈취된 JWT 는 만료까지 유효.
- **환경.** 로컬과 테스트 환경만 씁니다. 운영 데이터·실제 계정·유료 외부 API 는 쓰지 않습니다.
  - DeepL 은 목(mock) 서버로, Azure Blob 은 Azurite 에뮬레이터로 대신합니다.
- **즉시 보고.** 치명 보안 결함이나 데이터 손실 결함은 발견 즉시 알리고 이어서 진행합니다.

## 2. 위험 평가 — 무엇을 먼저 보나

이전 세 차례 점검은 설계 검토 위주였고, 위험이 큰 곳은 대부분 회귀 테스트로 고정됐습니다. 이번 QA 는 **블랙박스로 체계적으로 훑어서** 사람이 검토하다 놓치기 쉬운 조합을 찾는 데 무게를 둡니다.

| 순위 | 위험 | 왜 | 점검 가설(아직 결함 아님) |

## 3. 점검 방법 (영역별)

### 3-1. 보안 (Q1, 가장 먼저)

1. **인가 행렬 시험 (백엔드 통합 테스트 `qa/AuthorizationMatrixTest`)**
   - 사용자 A·B·C 와 팀 두 개를 준비합니다.
   - 64개 엔드포인트마다 "주인·같은 팀 읽기 전용·다른 팀·비로그인" 으로 요청해, 기대 상태 코드(200/403/404/401)와 **부수 효과가 없는지**(DB 재조회)를 확인합니다.
   - ID 를 섞는 조합(위 순위 1)을 모두 넣습니다.
2. **인증·세션**
   - 탈퇴한 사용자의 쿠키로 요청합니다.
   - 서명 변조, `alg=none`, 만료, 다른 비밀키 토큰을 넣어 봅니다.
   - Bearer 헤더와 쿠키를 함께 보내 봅니다.
   - 쿠키 속성(HttpOnly·Secure·SameSite, 운영 프로필)을 확인합니다.
   - 로그인·공유 비밀번호 요청 제한을 우회해 봅니다(대소문자·공백·유니코드 변형 아이디).
3. **인젝션·입력 조작**
   - 검색·이름·채팅·초대 아이디에 SQL 조각, LIKE 와일드카드, 4바이트 문자, 아주 긴 문자열(1MB)을 넣습니다.
   - 경로·쿼리 ID 에 `-1`, `0`, `9223372036854775807`, `9223372036854775808`, `abc`, `1e3` 을 넣습니다.
   - JSON 에 타입 혼동(`"items": "x"`, 숫자 대신 문자열·배열), 알 수 없는 필드, `null` 을 보냅니다.
   - 기대 동작: 400/404 만 나오고 500 은 없어야 합니다. 오류 본문에 스택·SQL·내부 경로가 없어야 합니다.
4. **CSRF·XSS·헤더**
   - CSRF 토큰 없이·틀린 토큰으로 상태 변경 요청을 모두 보내 봅니다.
   - 업로드한 SVG·HTML·텍스트를 `view` 로 열어 스크립트가 실행되지 않는지 실제 브라우저로 확인합니다.
   - `Content-Disposition` 파일명 주입(CRLF·따옴표)을 넣어 봅니다.
   - 공유 페이지·채팅·팀 이름·알림의 XSS 를 확인합니다.
   - 전 경로의 보안 헤더(CSP·HSTS(운영)·X-Content-Type-Options·Referrer-Policy·frame-ancestors)를 확인합니다.
5. **비밀값**
   - gitleaks 로 전체 이력을 검사합니다.
   - 저장소·Docker 이미지 안의 설정 파일을 grep 합니다.
   - 오류 응답과 앱 로그(QA 중 수집한 전체 로그)에서 JWT·비밀번호·grant·공유 토큰을 검색합니다.
6. **의존성·지원 종료**
   - 도구: OSV-Scanner(Gradle·npm 잠금 파일), `npm audit`, Trivy(최종 Docker 이미지 OS 패키지).
   - 대상: Spring Boot 4.1·Java 21·Node 24·MySQL 8.4·React 19·기반 이미지의 지원 종료일.
   - 지원 종료일은 공식 일정 페이지에서 확인해 적습니다.

### 3-2. 데이터 손실·신뢰성 (Q2)

1. **동시 요청.** `TransactionRace`(잠금을 쥔 채 다른 요청을 보내는 결정적 재현)와 동시 스레드로 시험합니다.
   - 이동 vs 삭제, 복사 vs 대상 휴지통, 복원 vs 영구 삭제
   - 이름 바꾸기 충돌(같은 이름)
   - 업로드 vs 탈퇴
   - 초대 수락 vs 팀 삭제, 위임 vs 나가기
   - 같은 요청 두 번(더블 클릭) — 같은 폴더 두 번 만들기, 같은 초대 두 번 수락
   - 기대 동작: 행·파일 수, 사용량, 휴지통 표시가 어긋나지 않아야 합니다.
2. **장애 주입 (별도 QA 스택)**
   - DB 를 멈춘 채 요청(응답 코드·회복 시간)을 보내 봅니다.
   - Toxiproxy 로 DB·Azurite 에 지연·끊김을 넣습니다.
   - 업로드·복사·텍스트 저장 중 앱 컨테이너를 강제 종료(`kill -9`)합니다.
   - 재시작 뒤 DB 행 ↔ 저장소 파일 정합성 스크립트로 고아·유실을 집계합니다.
3. **외부 API**
   - DeepL 목 서버로 지연(35초)·5xx·연결 끊김을 만듭니다.
   - 응답 코드, 분량 반환, **호출 중 DB 커넥션을 붙잡는지**(커넥션 풀 고갈)를 확인합니다.
4. **백업·복원**
   - 문서에 백업 절차가 없습니다. → 4번 결정 D4.

### 3-3. 기능 경계값 (Q3)

- 모든 API 를 정상값·경계값·비정상값으로 시험합니다.
