# ADR-0018 계정 수(20개)와 한 계정의 팀 소속 수(6개) 상한 — 가입은 서버 안 잠금으로 줄 세움

## 배경
공개 데모(Azure 무료 계정 + App Service B1)의 저장 비용을 미리 막기 위해, 소유자가 가입할 수 있는 계정을 체험 계정 포함 20개로,
한 계정이 속할 수 있는 팀을 6개로 정했습니다. 그전에는 계정 수에 상한이 없었고(가입은 IP 당 시간당 5회만), 팀은 "팀장인 팀 10개"만 셌습니다
(S-10) — 멤버로 들어가는 팀은 끝없이 늘릴 수 있었습니다.

## 선택지
1. 동시 가입으로 상한을 넘지 않게 하는 방법
   - 시스템 계정 행(`deleted_user`, 늘 있음)을 DB 에서 잠그고 센 뒤 넣기 — 탈퇴가 데이터를 그 계정으로 넘기며 행을 참조(외래 키 공유 잠금)하는
     순서와 반대라, 같은 아이디의 재가입과 겹치면 교착될 수 있음
   - MySQL 이름 잠금(`GET_LOCK`) — 잠금을 쥔 커넥션을 트랜잭션과 따로 관리해야 하고, 인증 없는 경로에서 커넥션을 두 개씩 쥠(M-2)
   - 잠금용 표를 새로 만들기 — 스키마 변경(Flyway V5)
   - **서버 안의 잠금(공정한 `ReentrantLock`)** — 운영은 인스턴스 1개(B1). 요청 제한기·AI 동시 실행 상한(ADR-0012)과 같은 전제
2. 체험 계정을 셀지 — **센다**(소유자 요구 "데모 포함 20개"). 다만 매일 초기화가 체험 계정을 지웠다가 다시 만들므로, 체험 모드에서는
   체험 계정 3자리를 늘 남겨 둡니다. 남겨 두지 않으면 그 사이 일반 가입이 자리를 차지해 체험 계정을 다시 만들지 못합니다.
3. 팀 상한을 어디서 셀지 — 팀장인 팀만(지금) / **팀장·멤버 모두(속한 팀 수)**. 같은 설정 `MAX_TEAMS_PER_USER` 의 뜻을 넓히고 기본값을 6으로

## 결정
- 외부 가입은 상한을 먼저 빠르게 보고(꽉 찼으면 비밀번호 해시 없이 409), 잠금을 쥔 채 트랜잭션 안에서 다시 세고 넣고 커밋한 뒤 놓습니다.
  잠금은 10초 기다려도 못 얻으면 503. 관리·시스템 계정은 세지 않고, 체험 데이터 생성(서버 내부 가입)은 상한과 무관합니다.
- 팀 소속 수는 팀 만들기(사용자 행 잠금 뒤), 초대(받는 사람이 이미 6개면 409), 초대 수락(받는 사람의 사용자 행을 먼저 잠근 뒤)에서 셉니다.
  잠금 순서는 다른 경로와 같은 사용자 행 → 팀 행(ADR-0009). 팀장 위임·관리자 삭제의 "팀장인 팀 수" 확인(S-10)은 상한을 낮추기 전부터 더 많은
  팀에 속한 계정을 위해 남깁니다.
- 상한을 낮춰도 기존 계정·소속은 지우지 않습니다. 새로 가입하거나 팀에 들어가지만 못합니다.

## 결과
- 최대 저장량은 계정 20개 × 2GB + 팀 102개 × 5GB + 체험 팀 2개 × 2GB = 554GB, 저장비 월 약 15,000원(배포 문서 §6).
- 인스턴스를 늘리면 가입 잠금은 인스턴스마다 따로라 동시 가입이 겹칠 때 상한을 넘을 수 있습니다 — 그때는 잠금용 표나 `GET_LOCK` 으로 바꿉니다.
- 근거: `AccountLimitTest`(상한에서 409·동시 가입 8건 중 남은 자리만·체험 3자리 예약), `TeamMembershipLimitTest`(만들기·초대·수락·동시 수락),
  `TeamWorkflowTest`(S-10 을 새 상한으로).
