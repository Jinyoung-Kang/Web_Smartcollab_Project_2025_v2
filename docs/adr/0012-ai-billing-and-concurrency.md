# ADR-0012 AI 비용은 "최악값 예약 → 과금 여부에 따라 정산", 요약·번역은 동시 실행 수를 묶음

## 배경
ADR-0011 은 호출 전에 "입력 + 출력 예상분"을 예약하고, 성공하면 실제 사용량으로 정산하고 실패하면 예약을 돌려줬습니다. 종합 기술 리뷰에서 두 가지가 나왔습니다.
- **실패해도 과금되는 경우를 돌려줌 [H-2]**: 출력 한도에서 잘림·거절·형식 오류·스트림 끊김은 응답을 받은 뒤라 Anthropic 이 과금하는데, 예약을 전부 돌려줘
  같은 요청을 되풀이하면 하루 한도와 상관없이 계속 과금할 수 있었습니다. 번역의 출력 예상분도 실제 max_tokens(64,000)보다 작게 잡혀 동시 요청이 한도를 넘었습니다.
- **동시 실행에 상한이 없음 [M-1]**: 한 사용자가 여러 탭에서 큰 PDF 를 동시에 요청하면 요청마다 문서·base64·요청 본문을 메모리에 올리고 API 를 불렀습니다.
  한도를 다 쓴 사용자도 문서를 읽고 토큰을 센 뒤에야 거절됐습니다.

## 선택지
1. 정산: 실패는 모두 환불(이전) / 실패는 모두 예약분 차감 / **과금 전 실패만 환불, 응답을 받은 뒤의 실패는 실제 사용량(모르면 예약분 전부)**
2. 예약 크기: 평균 예상치 / **요청의 max_tokens 와 같은 최악값** — 동시에 보낸 요청도 한도를 넘지 못함
3. 동시 실행: 큐(대기) / 메시지 브로커 / **사용자당·서버 전체 세마포어로 바로 거절(429·503)** — 새 인프라 없이, 짧은 작업이라 대기열보다 재시도가 단순

## 결정
- 예약 = 입력 토큰 + 출력 상한. 출력 상한은 요약 8,000, 번역 `min(64,000, 입력 × 3 + 4,096)` — 요청의 max_tokens 에 같은 값을 씁니다.
- 응답을 받은 뒤의 실패는 `DocumentAi.BilledFailure`(과금 토큰, 모르면 null)로 올려 그만큼(null 이면 예약분 전부) 남기고, 과금 전 실패만 돌려줍니다.
- 결과 캐시를 놓친 요청은 남은 한도가 가장 작은 예약에도 못 미치면 문서를 읽기 전에 429. 그다음 사용자당 2건(넘으면 429)·서버 전체 `AI_MAX_CONCURRENT`
  (기본 8, 넘으면 503) 슬롯을 얻은 뒤에만 문서를 읽고 부릅니다. 8은 10MB PDF 하나가 잠깐 수십 MB 를 쓰는 것을 기준으로 2GB 컨테이너에 맞춘 값입니다.
- 번역은 스트리밍이라 전체 시간 상한(`AI_TRANSLATION_TIMEOUT`, 10분)을 요약·토큰 세기의 상한(`AI_TIMEOUT`, 120초)과 따로 둡니다.

## 결과
- 같은 요청을 되풀이해도 하루 한도 안에서만 과금됩니다. 대신 잘린 번역처럼 결과를 돌려주지 않은 요청도 한도를 씁니다(실제로 과금되었으므로).
- 최악값 예약이라 남은 한도가 출력 상한보다 작으면 실제로는 짧게 끝날 요청도 거절됩니다 — 한도(기본 300,000)에 비해 상한이 작아 받아들였습니다.
- 슬롯과 한도는 서버 메모리라 인스턴스마다 따로입니다(요청 제한기·결과 캐시와 같은 전제, ADR-0011).
- 근거: `DocumentToolsTest`(과금된 실패·한도 소진 뒤 429)·`DocumentToolsConcurrencyTest`, 요청 메모리 측정 `qa/results/review-2026-10-12/m1-pdf-allocation.txt`.
