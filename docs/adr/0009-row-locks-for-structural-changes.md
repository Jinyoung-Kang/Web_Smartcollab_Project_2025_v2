# ADR-0009 짧은 구조 변경은 저장 공간·파일 행 잠금으로 차례로 처리

## 배경
3차 점검에서 동시 요청이 각자 트랜잭션 시작 때의 스냅샷으로 판단해 데이터를 망가뜨리는 경로를 재현했습니다(REVIEW_2026-10-03 S-06·S-17).
- A→B, B→A 폴더 이동이 동시에 일어나면 순환이 생겨 그 폴더와 팀·계정을 지울 수 없게 됨
- 폴더를 휴지통에 넣는 동안 하위 폴더 이름을 바꾸면, 이름 변경의 전체 열 UPDATE 가 휴지통 표시를 지움 → 30일 뒤 "살아 있는" 폴더까지 영구 삭제
- 휴지통에 들어가는 폴더 아래에 동시에 새 폴더가 생김
- 문서 저장·버전 복원과 서명이 겹치면 밀려난 버전에 유효한 서명이 남음

ADR-0006 의 낙관적 잠금은 "편집 세션이 긴" 텍스트 편집에 맞춘 것입니다. 위 작업은 요청 하나 안에서 끝나는 짧은 변경이고, 판단에 쓰는 데이터가
여러 행(조상 경로·하위 트리)에 걸쳐 있어 한 행의 `@Version` 으로는 경합을 잡을 수 없습니다.

## 선택지
1. 행마다 `@Version` — 순환·하위 트리 판단은 여러 행을 읽으므로 막지 못함
2. 분산 잠금·큐(Redis 등) — 단일 인스턴스 전제에 새 인프라가 필요
3. **이미 있는 행을 잠가 차례로 처리** — 저장 한도 확인에 쓰던 저장 공간 주인 행(사용자/팀)과 파일 행

## 결정
- **폴더 구조 변경**(생성·이동·복사 반영·휴지통·복원·영구 삭제·휴지통 비우기·자동 비우기)은 `FolderStructureLock` 으로 저장 공간 주인 행을
  엔티티를 읽기 **전에** 잠그고, 트랜잭션은 READ COMMITTED 로 실행해 잠근 뒤의 최신 데이터로 다시 판단합니다.
  READ COMMITTED 가 아니면 예외를 던져 잘못된 사용을 막습니다.
- 폴더 엔티티는 `@DynamicUpdate` 로 바뀐 열만 UPDATE 합니다(스키마 변경 없음).
- **문서 내용 변경과 서명**은 파일 행을 잠급니다. 서명·복원은 파일 행을 먼저 잠그고 최신 현재 버전을 읽고, 저장은 새 버전 행을 넣기 전에 잠급니다
  (새 버전 INSERT 의 외래 키 확인이 파일 행에 공유 잠금을 건 뒤 UPDATE 가 배타 잠금으로 올리는 사이에 서명과 교착되지 않게).
- **잠금 순서**: 저장 공간 행 → 파일 행. 여러 저장 공간을 잠글 때는 사용자 행 다음 팀 행, 각각 ID 순.
- 같은 방식으로 "팀장인 팀 수" 확인도 사용자 행을 잠근 뒤 셉니다(S-10).

## 결과
- 같은 저장 공간의 구조 변경은 차례로 처리됩니다. 잠그는 작업은 요청 하나 안에서 끝나는 짧은 DB 작업뿐이고(저장소 입출력은 트랜잭션 밖), 다른 저장 공간과는 서로 기다리지 않습니다.
- 경합은 `support/TransactionRace` 로 결정적으로 재현해 테스트합니다(다른 트랜잭션이 잠금을 쥔 채 기다리는 동안 요청을 보냄).
- 여러 인스턴스로 늘려도 DB 행 잠금이라 그대로 동작합니다. 긴 작업(대량 복사)은 저장소 작업을 트랜잭션 밖에서 하고 반영만 잠근 채 합니다.
